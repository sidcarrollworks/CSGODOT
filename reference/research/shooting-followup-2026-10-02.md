# Shooting follow-up: actions, zoom, landing and camera

Continuation of the [October 2 shooting audit](shooting-audit-2026-10-02.md),
using the same installed build **1.41.8.8 / 2000922 / SourceRevision 11064488**
and the DLL hashes recorded there. Addresses are preferred PE virtual
addresses with image base `0x180000000`. This is research for R3, R4, R6
and R13; it changes no gameplay and completes no implementation checkbox.

The four follow-up traces recover the silencer completion event, the
scope's mode/floor transition, fall-speed landing penalties and first-person
camera composition. Remaining local captures validate tick/event ordering,
playback timing and how the recovered behavior looks in motion.

## Silencers: state change and firing unlock are different events

**Data + binary.** Both freshly decoded variations,
`animation/graphs/viewmodel/viewmodel_gun.vnmgraph+m4a1s.vnmgraph_c` and
`viewmodel_gun.vnmgraph+usp.vnmgraph_c`, have:

- `actions/Actions/SM/SilencerOff` at node **53**, playing child **54**;
- `actions/Actions/SM/SilencerOn` at node **106**, playing child **107**;
- non-looping clips, authored speed multiplier **1.0**;
- a timed-remaining **`WPN_ACTION_COMPLETE`** event at **remaining <= 0.1 s**.

The graph resource slots resolve to the default rifle/pistol silencer clips
already decoded in the main audit. Their attach/detach ID events change
the silencer flag and mode. Completion is generated by the graph state,
so looking only for an extra completion event inside the clip misses it.

The event collector sets output byte `+0x2b4` for `WPN_ACTION_COMPLETE`.
The weapon consumes that output, invokes its completion method, and
returns actions **600/601** to idle **50**. Leaving either silencer action
resets primary and secondary readiness, silencer-complete time, and the
owner's next-attack gate to current simulation time. The completion method
also restores weapon playback rate to 1.0. The initial **100 s** gate is
therefore a blocking placeholder, not the silencer duration.

**Binary.** The holster path calls the base holster, which changes the action
to **10**; leaving 600/601 runs the same gate cleanup. That path does not
force the silencer flag to the requested final value. Interrupting before
the clip's attach/detach event leaves the earlier flag; interrupting after
it keeps the event's new flag. A newly selected weapon can subsequently
apply its own deploy gates; cleanup is not proof of an instant next shot.

**Implementation gap.** R3 needs separate event-driven state changes and
completion/cancellation. At clip speed 1, a 4.8333 s source clip reaches
the graph's threshold around **4.7333 s of clip progression**, not at the
3.2666–3.4333 s state-change event. This is a resource-derived threshold,
not a measured wall-clock firing delay: graph entry/blending, effective
playback speed and event/command ordering still need local validation.
Check switching on each side of both events and returning to the weapon.

## Scope accuracy settles through the shared penalty

**Binary, client/server agree.** The generic zoom handler changes weapon
mode to **1** when scoped and **0** when unscoped, immediately in the
handler. It requests camera FOV separately with the appropriate authored
`ZoomTime` (and handles the ironsight controller separately). Standing and
crouching getters directly read their raw two-value arrays by mode; they
do not interpolate those values with FOV or zoom progress.

The existing accuracy penalty survives a zoom change. The accuracy update
selects the new mode/stance floor and uses the shared recovery formula:

```
if P < new_floor: P = new_floor
else: P = new_floor + (P - new_floor) * exp(-ln(10) * dt / recovery_time)
```

Thus a lower scoped floor does not remove the previous hip-fire penalty
immediately. It approaches that floor at the weapon's recovery rate;
unscoping to a higher floor raises the penalty on the next accuracy update.
The existing movement/air terms also read the current mode. All six scoped
firearms' inspected vtables use these shared accuracy methods; the trace
does not require a separate AWP-specific override.

For example, fresh AWP data has standing floors **0.0808 / 0.002**,
initial standing recovery **0.34539 s**, and first zoom time **0.05 s**.
Those are different controls: reaching the narrow FOV does not establish
that the penalty has reached 0.002. Recovery time denotes tenfold reduction
of excess, not a hard deadline at which excess becomes zero.

The zoom handler resets `m_fAccuracySmoothedForZoom` (server `0xf90`,
client `0x1a20`) to zero. The recovered total/update paths do not read it;
its schema name alone is not evidence for a second linear accuracy blend.
This does not prove the field is unused in every possible path.

**Implementation gap.** Our `Weapon.scoped_share()` blends accuracy over
`ZoomTime`; its callers also blend landing and fire terms that way. The
recovered mode/floor behavior should replace that assumption as part of
R13, while FOV/viewmodel animation retains its own timing. Capture scoped
first shots across tick boundaries, a second zoom level, rezoom after a
bolt shot, movement and crouching before calling the port exact.

## Landing uses fall speed, adds a penalty, and also adds aim punch

**Binary, client/server agree on the weapon calculation.** Movement records
positive fall speed by negating downward Z velocity. Landing processing
passes stored `m_flFallVelocity` through the player landing handler to the
active weapon. That handler's accuracy operation is:

```
landing_delta = raw_InaccuracyLand[current_mode] * processed_fall_speed
accuracy_penalty += landing_delta
```

There is no subtraction of standing inaccuracy and no `max(old, delta)` in
that weapon operation. The movement path can reduce the fall speed for a
downward-moving supporting entity before dispatch; preserve that boundary
rather than treating every ground contact as a full jump. The speed is in
Source movement units per second; multiplying a
Godot metre-per-second value directly would give the wrong penalty.

The increment enters the same persistent `P` as firing. After landing it
recovers toward the current grounded stance/mode floor with the R13
recovery time. It is not a separate landing-only decay timer. For example,
AK data's coefficient **0.000242** with a processed fall speed of **300**
adds **0.0726** in raw cone units, before later recovery/clamping.

The landing handler also computes an angular aim-punch contribution from
the increment: pitch is **0.2 * degrees(asin(clamp(delta, -1, 1)))**; yaw
is that pitch times **0.1** and a named random draw in **[-1, 1]**
(`LandPunchAngleYaw`). It adds this through the aim-punch service.
The [-1,1] clamp is for `asin`, not a clamp on the earlier stored increment.
Movement additionally has a separate view-punch branch for certain falls;
the two paths must not be conflated with the accuracy coefficient.

**Implementation gap.** Our ground-contact transition uses the spreadsheet
landing cone minus standing cone, takes `max`, and does not carry fall
speed into that calculation. A port needs the raw coefficient and processed
landing speed as simulation inputs, then the shared state-floor recovery.
Check low drops, a jump, a taller fall, crouched landing, a moving support,
and landing during a spray. Validate bullet accuracy separately from the
already accepted jump/landing viewmodel animation.

## Camera recoil has a scaled aim channel and a separate view channel

**Binary.** In the normal living first-person camera path `180882790`,
the camera reconstructs and combines predictable/unpredictable aim punch
through `1808533c0`. Its reconstruction requests the **2x** angle scale
already established for bullet aim. It then multiplies the composed result
by **0.45**, adds it to view angles, and separately adds decayed view punch.
The scale is applied after aim-punch composition; retain that order.
Death, observer, replay and third-person branches are outside this finding.

**Binary, client/server agree.** A firing impulse also modifies the current
view-punch pitch/yaw by cosine/sine of recoil angle times recoil magnitude
times **0.055**, using the same subtracting axis signs as the aim impulse.
The view-punch setter normalizes angles and stores the shot tick/fraction
with the camera-service state. View punch decays exponentially as
**`exp(-18 * elapsed_seconds)`** at the registered default
`view_punch_decay = 18`. This is separate from aim punch's 8/18/4.5 model;
the 0.055 is not a new multiplier on bullet spread or aim-punch velocity.

`sv_suppress_viewpunch` registers **false**. When true it skips writes to
the view-punch state; it does not stop the preceding aim-punch impulse
update or suppress bullet aim. Existing view-punch state can still decay
through the camera reader, so toggling it is not proof that all current
camera recoil instantly vanishes. The camera continues to use its aim
channel.

**Implementation gap.** Our camera is tuned with fast/slow cosmetic springs,
so replacing their constants alone would not reproduce this composition.
Port/validate numerical aim recoil first, then compare the camera with the
0.45 composition scale and separate 0.055/18 view channel. The viewmodel's
own recoil and scope framing remain separate visual work. Capture a held
spray/release and a single shot with suppression off/on to verify signs,
relative weights and displayed interpolation.
